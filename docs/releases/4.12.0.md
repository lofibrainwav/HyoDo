# HyoDo 4.12.0 release notes and receipt plan

## Summary

HyoDo 4.12.0 is the release-trust and external-consumption seal after the 4.11.0 MCP access-ledger release.

This release does not rewrite the historical unsigned `v4.11.0` tag. It establishes the forward-going public release chain:

```text
verified tag -> draft Release -> SBOM evidence/readback -> human Publish Release -> release:published -> PyPI OIDC
```

## Added

- CI-only Hypothesis reproducibility profile that keeps local Hypothesis exploration and local databases intact.
- Status-aware mutmut 3.7.0 mutation receipt parser and sealed full-core mutation census.
- Cosmic Ray scoring mutation automation with advisory PR feedback and scheduled/manual full-core execution.
- Pre-commit discoverability hooks for `hyodo check` and `hyodo safe --strict`.
- Same-ref composite GitHub Action for external consumers.
- SARIF 2.1.0 report output for measured HyoDo findings.
- Consumer smoke tests for pre-commit and the composite action.
- Verified annotated release-tag gate before PyPI publication.
- Immutable-release-safe exact-tag SBOM evidence workflow.

## Changed

- PyPI publication no longer starts from tag push alone.
- PyPI publication now requires a published GitHub Release with durable `sbom.cyclonedx.json` and `sbom.cyclonedx.json.sha256` assets.
- The PyPI build independently downloads and verifies the release SBOM checksum before building distributions.
- Mutation workflow PR triggers are narrowed to the scoring-relevant surfaces so release/docs-only PRs do not pay the expensive advisory mutation run.

## Fixed

- Hypothesis CI reproducibility no longer disables local exploratory behavior.
- Mutation scoring no longer collapses timeout, skipped, not-checked, no-test, interrupted, segfault, type-check, and suspicious outcomes into a fake denominator.
- `-24` mutmut status is treated according to the effective mutmut 3.7.0 status map instead of being counted as killed.
- Release evidence publication avoids destructive `--clobber` behavior.
- Published releases missing durable evidence fail closed instead of being mutated after publication.

## First real release receipt checklist

This checklist was written before 4.12.0 shipped and was **never reconciled**
afterwards, so every box below is unticked while the release itself
demonstrably happened: tag `v4.12.0` -> `2cc561a`, GitHub Release published
2026-09-06T05:43:02Z, and `4.12.0` present on PyPI. The boxes are left as
written rather than ticked now, because nobody observed them at the time and
inventing the observation is the failure a receipt exists to prevent.

Releases from 4.19.1 on carry a measured receipt instead
(`scripts/release/verify_release_chain.py`), where an unmeasured step reads
`UNOBSERVED` rather than as a box that silently rots into a false claim.

- [ ] Merge the 4.12.0 version-prep PR after CI and smoke are green.
- [ ] Confirm latest `main` CI and smoke are green.
- [ ] Create a signed annotated tag `v4.12.0` from the release commit.
- [ ] Confirm GitHub reports the tag as Verified.
- [ ] Create a draft GitHub Release for `v4.12.0` using these release notes.
- [ ] Manually dispatch `HyoDo Release Evidence` for `v4.12.0`.
- [ ] Confirm the workflow attaches both durable release assets.
- [ ] Confirm release asset readback verifies byte equality and SHA-256.
- [ ] Publish the draft Release by human action.
- [ ] Confirm `release: published` starts the PyPI Trusted Publishing workflow.
- [ ] Confirm PyPI provenance and cold install smoke pass.
- [ ] Paste the end-to-end receipt into issue #129 and close it.
