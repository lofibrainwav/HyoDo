# HyoDo 4.19.2 Release Notes

## Intent

4.19.1 shipped Cursor and Codex host adapters that map one tool call into two
canonical events — `tool_call` from the pre hook, `tool_result` from the post
hook. Both derived their `event_id` from the host's `tool_use_id` verbatim, so
the ledger's idempotency check read the second write as a conflict and refused
it. Half of the observation spine was dropped in silence, and the CLI reported
it as a refusal rather than a defect.

This patch qualifies the host-supplied id as `{host}:{event_name}:{tool_use_id}`
— the shape the specialized-hook digest path already used. Each canonical event
carries its own identity while the tool id stays the correlation anchor between
the two halves. Nothing else changes.

The mapper was correct the whole time: it really did produce `tool_call` and
`tool_result`. The collision only existed at the ledger boundary, and no test
crossed that boundary, so every fixture passed. This release adds one that does.

## Scope of the claim

Live Cursor and Codex callback observation remains `UNOBSERVED`. This release
makes the two-event path recordable; it does not claim an installed host emitted
it. A live canary run against this published package is the next step.

Cursor requires its own independent canary. A Codex receipt does not promote
Cursor to observed — each host is verified on its own surface, and a host that
has not been observed is not claimed as supported.

## Live canary

Measured against the published package, not the checkout: a clean venv with
`pip install --no-cache-dir hyodo==4.19.2`, one Codex-shaped tool call fed
through `hyodo event record --hook codex` as both halves.

```
PreToolUse    exit=0  event_id='codex:PreToolUse:tool-1'
PostToolUse   exit=0  event_id='codex:PostToolUse:tool-1'
ledger        2 lines  ['tool_call', 'tool_result']
```

The same script run against 4.19.1 from PyPI records one line and refuses the
second with `exit=2`, so this is a check with teeth rather than one that
passes by construction.

This observes the recording path on the shipped artifact. It does not observe
a live host: the payload is synthetic, fed to the CLI rather than emitted by
an installed Cursor or Codex process. Live callback observation for both hosts
remains `UNOBSERVED`.
