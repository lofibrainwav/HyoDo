# HyoDo 4.19.9 Release Notes

## Intent

Publish the storefront repairs from the 2026-09-19 first-visit audit so the
published package stops contradicting its own documentation.

Two of the three audit P1 items were already visible to a visitor once the
source merged, because the website redeploys on merge: the hero layout repair
and the quickstart guidance are live at `hyodo.app`. The third is not. The
published description still carries 18 relative links that 404, so a reader who
arrives from PyPI cannot open Quick Start, the gate syntax reference, or the
licence. That is what this release closes.

## Scope of the delta since 4.19.8

The version bump itself carries no runtime change, but the release does. The
storefront repair is not the only thing that reached `main` since 4.19.8, so what
an installer receives is the whole delta, measured with
`git diff v4.19.8..v4.19.9`:

- 17 files and +1881 / -67 under `hyodo/`.
- Seven new modules: `compute_supply_observation`, `evidence_plate`,
  `factorial_benchmark`, `independent_verifier`, `nameplate`,
  `six_lens_runtime`, `verification_view`.
- The local dashboard gains one route, `/api/verification-view`.

What was measured about compatibility, and all that is claimed here:

- CLI command set unchanged: 40 commands before and after, same names, none
  removed or renamed.
- MCP tool set unchanged: the same six tools, same names.
- The documented exit-code contract is unchanged: every row of the
  `QUICK_START.md` exit-contract table is identical to 4.19.8. The file itself
  did change, but only in the MCP-extra sentence this release repairs.

Those three are compatibility statements, not a claim that behaviour is
identical. The additions above arrived through their own reviewed pull requests
and `CHANGELOG.md` is the record of them.

## Rollback

PyPI supports both deleting and yanking a release; they are different
operations. Deletion is permanent, frees project storage, and breaks installation
for anyone pinned to that version. Yanking leaves the files in place and
installable by an exact pin, and only tells resolvers not to choose the version
for a range.

The policy for this release is **yank, not delete**, so a failed artifact stays
inspectable as evidence. If the post-publish readback fails: yank `4.19.9`, leave
the tag and GitHub Release in place, and record the failure here before any
retry.

A yank is not a rollback of anything already installed. An environment that
already has `4.19.9` is not downgraded by it, so falling back to `4.19.8`
requires an explicit reinstall, verified as its own step. Note also that
`4.19.8` keeps the broken description links — a yank restores the last working
install, not the last correct storefront.
